# История разработки Suflyor и восстановление ветки до master2

Дата восстановления: **30 октября 2026 года**. Источники: ранее обсуждавшиеся сборки и ошибки Windows, сохранённые ZIP-пакеты, архив исходников v8.2, 5 последовательных patch-файлов, архив диагностики v11.8, а также оригинальный `master` 0.39.0. Хронология описывает подтверждённые в доступных источниках контрольные точки, а не является полной историей всех Git-коммитов.

## Главный вывод

Существовали **две разные линии**. `master` v0.39.0 — целый архив исходников основной ветки (966 записей в ZIP), но без части функций из пользовательской экспериментальной линии, включая дополнительные STT-провайдеры и Codex Direct. `Suflyor-Recovered-v8` — пользовательская ветка, восстановленная из экспортов кода 17 и 18 октября; в ней эти функции уже присутствовали. `master2` и ошибочные слияния 29 октября исключены из восстановленного дерева. Смешивать их без специальных тестов нельзя.

**Последняя подтверждённая собранная база пользовательской линии**: восстановленная v8.2, `overlay-host.exe` от 27.10.2026 00:59:24 (в отчёте пользователя; около 164,9 МБ). Это свидетельствует об успешной сборке EXE, но не доказывает тестирование всех функций. По более поздним источникам упоминалась успешная компиляция v11.3, но без отдельного подтверждения полноценного runtime. v11.8 дошла до сборки, затем сообщалось о `0xc0000005`; успех не подтверждён.

**Последний восстановленный снимок исходников** в этом пакете: v8.2 + v9 + v10 + дополнения от 21 и 26 октября + диагностика v11.8. Этот снимок **НЕ прошёл компиляцию на Windows в текущей среде**. Он не должен обозначаться как проверенный бинарный релиз.

## Как восстановлен исходный код в этом архиве

1. Взят `suflyor-recovered-source-v8.zip` из `Suflyor_UI_v8_2_recovery.zip` (полные исходники: 293 файла).
2. Применён `Suflyor_Proxy_Fallback_v9.zip` (git patch) с успешной проверкой `git apply --check`.
3. Применён `Suflyor_Recording_MiddleClick_v10.zip` (git patch), тоже без конфликтов.
4. Применены отдельно доступные патчи `suflyor-debrief-retry-v1.zip`, `suflyor-ai-mode-visibility-v1.zip`, `suflyor-ptt-feedback-race-fix-v1.zip`. Каждый прошёл проверку Git patch и был применён к копии.
5. Для `Suflyor_Diagnostics_v11_8_Targeted_UI_Repair(2).zip` исходники `network.rs`, `stt.rs`, `diagnostics.rs`, `settings_panel.slint` по нормализованному тексту точно соответствовали контрольным `payload/base/` пакета. Применены `payload/new/` для первых трёх файлов, а для Slint — прицельные изменения деклараций и вкладки диагностики по логике установщика (без замены других вкладок).
6. Проверено существование ключевых `.rs`, `.slint`, `Cargo.toml` и корректное чтение TOML. Git конфликтных маркеров в файлах исходников не обнаружено.

### Что не гарантировано

- Это исходники, **не готовый Windows EXE**. Здесь отсутствует Windows Rust/Cargo, поэтому `cargo build --bin overlay-host` не был выполнен. Предыдущий Windows сбой с `0xc0000005` может повториться.
- v8.2 восстановлена из экспортов 17/18 октября: не все локальные изменения, которые могли быть внесены вручную после этих дат, доступны. Только указанные отдельные патчи восстановлены поверх этих экспортов.
- Нельзя доказать, что пользователь действительно установил все патчи v9–v11 на один и тот же локальный worktree без последующего отката. Этот снимок — **воспроизведённая линия исходников по сохранённым артефактам**, а не образ установленного компьютера.
- Исправления и новые компоненты upstream `master` v0.39.0 не добавлялись, чтобы не потерять индивидуальные STT-страницы, Vision и скриншоты; сам upstream исходный архив сохранён отдельно.
- Нет записи о полной готовности функций Direct OAuth, Vision, proxy при реальных запросах и настройки диаризации на этой восстановленной ветке.
- Настройки и API-ключи не включены. Приложение использует `%APPDATA%\suflyor\config.json`, который этот архив не изменяет.

## Сборка на Windows

После распаковки `suflyor-recovered-last-pre-master2.zip`, перейти в `suflyor-recovered-last-pre-master2\slint-experiment` и выполнить:

```powershell
$env:CARGO_INCREMENTAL='1'; $env:CARGO_BUILD_JOBS='2'; cargo build --bin overlay-host
```

Зависимости компилируются только если их нет в текущем `target`. Включение другого `CARGO_TARGET_DIR` может замедлить первую сборку. При отсутствии готового Skia бинарника может понадобиться исправить его скачивание, но это не связано с source merge.
